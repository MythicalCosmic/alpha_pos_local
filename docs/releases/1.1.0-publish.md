# Alpha POS 1.1.0 — publish runbook

1.1.0 replaces the pywebview launcher with the Tauri shell, a windowless
backend and Discord-style startup updates. It reaches existing tills two ways:

- **1.0.x tills** get it through their old tufup updater (operator clicks
  "Install now" once). The published bundle is the Tauri install layout, so the
  old helper swaps folders, launches the new `AlphaPOS.exe`, and the shell
  confirms health by deleting `update_pending.flag` once the backend serves.
- **1.1.x tills** update themselves at startup from
  `https://control.78.111.91.113.nip.io/updates/tauri/stable/latest.json`.

Do not publish until the one-PC trial of the rc installer is confirmed.

## 1. Build (Linux host)

1. `python tools/sync_version.py --check` (version `1.1.0` everywhere).
2. Freeze the backend under Wine: `.release-builds/1.1.0-dev/build_backend_wine.py`
   (PyInstaller `AlphaPOSBackend.spec`, frozen selftest, lifecycle smoke) and copy
   `dist/AlphaPOSBackend` into the repo `dist/`.
3. Build the guard for Windows and copy it to
   `desktop-shell/src-tauri/resources/bin/alphapos-update-guard.exe`.
4. Build the signed installer in the `alphapos-tauri-build` image with
   `TAURI_SIGNING_PRIVATE_KEY[_PASSWORD]` from `update_keys/tauri-updater.*`:
   `cargo tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc --bundles nsis --config src-tauri/tauri.release.conf.json`
   → `Alpha POS_1.1.0_x64-setup.exe` + `.sig`.
5. Verify: `wine_install_test.py` (install over 1.0.46 leftovers), the E2E guard
   test in `.release-builds/1.1.1-e2e/`, and a green `Desktop (Windows)` CI run.

## 2. Bridge bundle for 1.0.x (tufup)

1. `python tools/stage_tauri_layout.py --shell <target>/release/AlphaPOS.exe --backend dist/AlphaPOSBackend --guard <target>/release/alphapos-update-guard.exe --out dist/tauri-layout`
2. Under the Wine build venv: `python tools/release.py --publish --bundle dist/tauri-layout`
   (targets/snapshot/timestamp now expire after 180 days; the root is unchanged).
3. Check `update_repo/metadata` versions increased and the `AlphaPOS-1.1.0.tar.gz`
   hash matches the targets entry.

## 3. Tauri updater manifest

`python tools/make_latest_json.py --installer "<nsis>/Alpha POS_1.1.0_x64-setup.exe" --base-url https://control.78.111.91.113.nip.io/updates/installers/ --notes "…" --out dist/latest.json`

## 4. Promote on the control host (`/srv/alpha_pos_updates`)

Stage everything under a `.staging-1.1.0-<date>` folder first, record the live
metadata hashes, then under `.release.lock` (same pattern as
`.release-builds/tuf-resign-20260916/publish.sh`):

1. `installers/AlphaPOS_1.1.0_x64-setup.exe` and its `.sig`
   (published name has no spaces; `latest.json` points at it).
2. tufup: `targets/AlphaPOS-1.1.0.tar.gz`, then `metadata/targets.json`,
   `snapshot.json`, `timestamp.json` last — after backing up the old metadata to
   `.history/`.
3. `tauri/stable/latest.json` last.

Verify over HTTPS: TUF client refresh against the live root, `latest.json`
parses and its signature verifies with the embedded key, installer hash matches.

## 5. After publishing

- Heartbeats carry `metrics.desktop_shell` (shell version, WebView2 version,
  blocked versions, last rollback) in the control center heartbeat payloads.
- A version that fails its health check is blocked per till and the rollback is
  recorded. **Not yet implemented:** automatic reinstall of the last known good
  installer — until then a failed update leaves the new files in place (blocked),
  and support reinstalls with the previous Setup.
- Manual recovery: run the previous installer (1.0.46 Inno Setup or a previous
  NSIS setup) into the same folder; data in `%LOCALAPPDATA%\AlphaPOS` is kept.
- Re-sign the TUF online metadata before 2027-03-14 while 1.0.x tills remain.
